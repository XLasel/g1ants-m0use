# Архитектура решения

## Контекст

Запись обрабатывается на Android без сети. Общий контракт данных и событий
находится в `:core`, последовательность этапов — в `:pipeline`, интерфейс — в `:app`.
Диагностический `:bench` использует тот же pipeline и сохраняет замеры отдельно
от JSON задания. Веса готовятся на компьютере и включаются в APK; на телефоне
копируются во внутреннюю память для ONNX Runtime и mmap llama.cpp.

## Компоненты

| Модуль | Ответственность |
|---|---|
| `core` | Слова, сегменты, реплики, пункты конспекта, события и JSON задания |
| `speech` | MediaCodec, перевод в 16 кГц моно, GigaAM через sherpa-onnx |
| `diarization` | Признаки, Nemotron, планирование кусков, совмещение слов и голосов |
| `summary` | Экстрактивный конспект, контекст, грамматика, проверка ссылок |
| `summary-android` | llama.cpp CPU/JNI, локальный GGUF, coroutine-адаптер и отмена |
| `pipeline` | Координация одного файла и события для интерфейса |
| `app` | Импорт/запись, очередь, сохранение, воспроизведение и экспорт |

### Чтение и распознавание

MediaCodec декодирует локальный файл; PCM сводится в моно и ресемплируется до
16 кГц. Огибающая RMS нужна для отображения. Вероятности Nemotron задают куски
речи для GigaAM. ASR выдаёт слова с началом/концом в миллисекундах; затем
`TranscriptMerger` присваивает каждому слову один голос и собирает реплики.

Кодек работает в асинхронном режиме, перевод в float и пересчёт в 16 кГц идут
сразу в его потоке. AAC и Opus длиннее 20 с читаются четырьмя кусками
параллельно: кусок начинается на 0,5 с раньше стыка, лишнее обрезается по номеру
отсчёта, соседние куски сравниваются в перекрытии, при расхождении запись
читается одним проходом. MP3 и Vorbis всегда читаются одним проходом: после
перемотки их кодеки сообщают время кадров неточно. Запись с диктофона на
14,5 минуты читается за 10 с вместо 70 с, результат совпадает бит в бит.

### Модели и копирование при первом запуске

| Модель | Задача | Формат | Размер | Среда выполнения | Лицензия |
|---|---|---|---|---|---|
| GigaAM v3 с пунктуацией (RNN-T) | Распознавание русской речи | ONNX, энкодер int8 | 232 МБ | sherpa-onnx 2.0.1 со встроенным ONNX Runtime | MIT |
| NVIDIA Nemotron 3 Diarization | Кто и когда говорит, до 8 голосов | ONNX, `step_int8.onnx` int8 | 106 МБ | `onnxruntime-android` 1.22.0 | уточнить |
| Qwen2.5-0.5B-Instruct | Название и конспект | GGUF | — | llama.cpp на CPU | Apache 2.0 |

Модели лежат в APK несжатыми (`noCompress` для `onnx` и `gguf`), а ONNX Runtime
и llama.cpp открывают модель по пути к файлу. Поэтому при первом запуске модели
копируются во внутреннюю память (`AssetModelInstaller`). Копирование начинается
сразу при открытии приложения, пока человек выбирает файлы (`LocalModels`), а
обработка ждёт его окончания: так первая обработка не тратит на это время и
модели не копируются дважды. Копия сохраняется один раз, прерванное копирование
при следующем запуске начинается заново. Папка копии модели конспекта зависит от
размера файла в APK: другая GGUF скопируется заново, а не возьмётся старая копия.

### Приложение (`app`)

Интерфейс на Jetpack Compose и Material 3 зависит только от `:pipeline` и типов
из `:core`.

| Часть | Что делает |
|---|---|
| Главный экран | Карточки записей с узорами голосов, кнопки «Записать» и «Загрузить» |
| Запись | `RecordingService`: `AudioRecord` 16 кГц моно в WAV, лента громкости, пауза; foreground-служба типа `microphone` пишет и при погашенном экране |
| Импорт | Системный выбор нескольких файлов, «Поделиться» и «Открыть с помощью» для `audio/*`. Выбранный файл копируется к себе: доступ по ссылке может пропасть, а звук нужен плееру и повторной обработке |
| Очередь обработки | `ProcessingQueue` обрабатывает записи по одной в порядке добавления и живёт в процессе приложения, а не на экране. `ProcessingService` (foreground, тип `dataSync`) держит процесс и показывает прогресс в шторке, поэтому обработка продолжается в свёрнутом приложении. Необработанные записи подхватываются при следующем запуске |
| Хранение | `RecordingsRepository` держит записи в памяти как `StateFlow` и после каждого изменения сохраняет их в один `recordings.json`. Записи с микрофона, оборванные закрытием приложения, восстанавливаются. Звук готовых записей можно удалить, расшифровки остаются |
| Расшифровка | Дорожки голосов, реплики, плеер со скоростью, переход к реплике, подсветка текущего слова, поиск слова, соло голоса, переименование |
| Конспект | Тема, решения, задачи со ссылками на моменты записи |
| Экспорт | JSON задания в «Загрузки» через MediaStore, без разрешений; имя как у исходного аудио, чтобы файл легко сопоставить с записью |

### Узор голоса

Каждому голосу рисуется узор — роза `r = cos(a/b · θ)` внутри «печеньки»
Material 3 (`VoiceRosette`). Форма зависит от высоты голоса: голоса записи
упорядочиваются от самого низкого к самому высокому, низкому достаётся узор с
меньшим числом лепестков (3, 5, 5, 7, 8, 8), высокому — с большим. Чем дольше
говорил голос, тем больше слоёв у розы. Пока высота не посчитана, узор
выбирается по порядку появления.

Высоту считает `VoiceFeatureExtractor` в `:diarization` по отрезкам каждого
голоса после диаризации, без нейросети: медиана основного тона алгоритмом YIN,
разброс тона (межквартильный размах в полутонах, октава = 1) и средняя громкость.
Результат приходит событием `SpeakerFeatures`.

### Координация и память

`process` — холодный Flow: подписка запускает обработку, отмена останавливает её.
Сначала диаризатор закрывается, затем загружается ASR, затем закрывается ASR
и загружается LLM. `Done` отдаёт готовую расшифровку до `Summary`; следующий
файл очереди запускается после окончания Flow. Ошибка LLM сохраняет транскрипцию.
Вся PCM-запись пока хранится в памяти, поэтому память приложения в целом растёт
с длительностью даже при ограниченном кэше моделей.

### Название и конспект

Готовые реплики копируются в `SourceUtterance`. Каждому фрагменту присваивается
ID и сохраняется связь с исходной репликой. Локальная Qwen через llama.cpp
генерирует название и выбирает ID темы, решений, задач. JSON-грамматика
разрешает только ID текущего набора; парсер проверяет их повторно.
Текст, время и голос пунктов подставляются из исходных реплик. Контекст
считается настоящим токенизатором с chat template. Длинные записи проходят
иерархический отбор исходных фрагментов, без молчаливого обрезания конца.

Название нормализуется и ограничивается шестью словами. Если оно слишком
короткое или непригодное, код берёт 3–6 слов выбранного источника либо нейтральное
«Краткий конспект разговора». Корректный конспект сохраняется при ошибке названия.
Конспект не корректирует ASR и не меняет экспортируемую транскрипцию.

### Диаризация (роль 3)

Модуль `src/android/diarization`, чистый Kotlin/JVM без Android-зависимостей. Подробности и цифры — в его README.

| Шаг | Класс | Вход → выход |
|---|---|---|
| Признаки | `LogMel` | Звук 16 кГц → лог-мел [кадры по 10 мс × 128] |
| Эмбеддинги | `NemotronDiarizer` + `embed.onnx` | Признаки → эмбеддинги [кадры по 80 мс × 512], блоками по 80 с |
| Спикеры | `NemotronDiarizer` + `step_int8.onnx`, `SpeakerCache` | Чанки по 27 с с кэшем спикеров → вероятности [кадры по 10 мс × 8] |
| Куски речи | `ChunkPlanner` | Вероятности → куски речи до 20 с для GigaAM, тишина выброшена |
| Совмещение | `TranscriptMerger` | Слова GigaAM + вероятности → спикер каждого слова → реплики |
| Экспорт | `TranscriptJson` | Реплики → JSON задания, `speaker_1` — кто заговорил первым |

Модель — NVIDIA Nemotron 3 Diarization, переведённая в ONNX (`embed.onnx` 2 МБ, `step_int8.onnx` 103 МБ, int8). Она различает до 8 спикеров и сама нумерует их по порядку появления.

**Кэш спикеров.** Запись обрабатывается чанками по 340 кадров (27 с) с правым контекстом 40 кадров. Перед каждым чанком модели подаются 264 «характерных» кадра уже найденных спикеров и 40 последних кадров (FIFO). Когда кэш переполняется, для каждого спикера остаются кадры, где он звучит увереннее всего, плюс эмбеддинг тишины. Поэтому спикер 1 в начале часовой записи остаётся спикером 1 и в конце, а память не растёт с длиной записи.

**Совмещение со словами.** Спикер слова — тот, чья средняя вероятность на интервале слова выше. Если на слове никто не говорит, окно расширяется на 0,5 с, а слова без активности берут спикера соседа. Затем одиночное «чужое» слово внутри плотной речи другого спикера возвращается ему, а смена спикера посреди предложения без паузы отдаёт предложение спикеру большинства, если диаризация в меньшинстве не уверена. Реплика — подряд идущие слова одного спикера с паузами до 2 с.

## Основные технические решения

**Диаризация:**

- Nemotron 3 Diarization вместо связки pyannote + TitaNet: на прототипе DER 2,3% против 15,6% на VoxConverse и 15,2% против 28,3% на русских диалогах, спикер слова верен на 100% против 53–88%.
- Диаризация идёт до распознавания: её вероятности задают куски речи для GigaAM, поэтому тишина не распознаётся, а разрезы не попадают в слова.
- Перенос на Kotlin сверен с Python-прототипом по шагам: признаки, эмбеддинги, кэш после каждого чанка, вероятности, реплики (`diarization/README.md`).
- Признаки и эмбеддинги считаются блоками по 80 с, результат совпадает с прогоном всей записи бит в бит. Память диаризации не зависит от длины записи.
- Модели загружаются по очереди: диаризатор закрывается до загрузки GigaAM.
- Пороги постобработки оставлены как в прототипе: перебор 14 параметров на 48 записях с шумом меняет итог в пределах ±0,5%.

## Зависимости

Android/Jetpack, Kotlin coroutines; GigaAM через sherpa-onnx с отдельным AAR;
llama.cpp закреплён на `cf659f240b232e15700b1721bbb43c1d973c52e9` и собирается
для ARM64 через NDK. У `summary` нет зависимости от Android UI или диаризатора.

**Диаризация:** ONNX Runtime (`onnxruntime-android` 1.22.0 на телефоне), модель NVIDIA Nemotron 3 Diarization (ONNX, int8). Других зависимостей у модуля нет, БПФ для признаков своё.

## Безопасность и приватность

Обработка не отправляет аудио и текст на сервер. Инструкции внутри расшифровки
передаются как данные; chat-маркеры экранируются в промпте, а исходный текст
остаётся неизменным. У LLM нет сетевых или файловых инструментов. Грамматика
и проверка ID ограничивают структуру ответа, но не доказывают правильность
названия или выбора важных фраз. Отдельные результаты проверки инъекции —
в `TEST_RESULTS.md`. Хранение записей и управление доступом выполняет приложение.
