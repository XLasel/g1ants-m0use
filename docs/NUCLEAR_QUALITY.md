# Проверка экспорта, WER и RTF

Python 3.10+, только стандартная библиотека. Установка пакетов, сеть и модели
не нужны. Инструмент работает с JSON, экспортированным Android-приложением,
и не вмешивается в код распознавания или интерфейса.

## Запуск

Из корня проекта:

```bash
python tools/nuclear_quality.py validate exported.json
python tools/nuclear_quality.py score --reference reference.txt --hypothesis exported.json --output reports/test_2.json
```

Эталон — вручную проверенный UTF-8 TXT или JSON в том же формате, что экспорт.
Без эталона можно проверить формат и время, но нельзя получить WER.

## Текущий benchmark Антона (роль 2)

В ветке `task-2-speech-recognition` экран `speechbench` сохраняет массив `words`,
длительности и параметры телефона. Это ещё не итоговый экспорт с говорящими.
Его можно проверить напрямую, без ручного превращения слов в реплики:

```bash
python tools/nuclear_quality.py score-bench --reference reference.txt --benchmark bench_test_2.m4a.4.json --output reports/test_2_asr.json
```

Сохранённый файл телефона соответствует `MainActivity.kt` из коммита `1dc8c38`:
`audio_seconds`, `processing_ms`, `words[{text,start_ms,end_ms}]`, `device`, `threads`,
`peak_rss_mb`. RTF пересчитывается как `processing_ms / 1000 / audio_seconds`;
расхождение с полем `rtf` или суммой `decode + load + asr` видно в предупреждениях.
Скрипт не выдумывает speaker-ID для такого файла.

Время этого benchmark охватывает декодирование, загрузку ASR и ASR.
Диаризация, LLM, копирование модели, огибающая и запись JSON в него не входят.
Такой RTF нельзя представлять как результат полной цепочки приложения.

Эталон должен быть размечен вручную или проверен вручную. Сравнение с другой
автоматической расшифровкой показывает расхождение версий, а не точность относительно
истины; существующий `src/android/scripts/compare_words.py` оставлен для этой задачи.

Чтобы добавить замер скорости, передайте фактически измеренные значения:

```bash
python tools/nuclear_quality.py score --reference reference.txt --hypothesis exported.json --audio-seconds 200.5 --elapsed-seconds 85.2 --device "PHONE_MODEL / RAM / ANDROID" --timing-scope "decode+diarization+asr+merge+export; cold models" --output reports/test_2.json
```

**Числа в этой команде условные; это пример синтаксиса, не результат проекта.**
Сам инструмент не запускает модели, не измеряет инференс и не подтверждает офлайн-работу.
RTF считается из переданных длительностей, а не из времени выполнения скрипта.

## Проверка самого инструмента

```bash
python -m unittest discover -s tests -p test_nuclear_quality.py -v
python tools/nuclear_quality.py validate examples/quality_fixture/hypothesis.json
python tools/nuclear_quality.py score --reference examples/quality_fixture/reference.txt --hypothesis examples/quality_fixture/hypothesis.json
python tools/nuclear_quality.py score-bench --reference examples/quality_fixture/reference.txt --benchmark examples/quality_fixture/android_benchmark.json
```

В искусственном примере четыре эталонных слова и одна намеренная замена
«важный» → «новый». Ожидается WER 25%. Это тест арифметики, не бенчмарк модели.

## Что проверяется

- Корневой объект и массив `transcript`.
- У каждой реплики: `speaker_id` и `text` — строки; `start_ms` и `end_ms` — целые числа.
- Логические ошибки времени: отрицательные значения и конец раньше начала.
- JSON с повторяющимися ключами, NaN или Infinity отклоняется.
- Перекрывающиеся реплики разрешены: перебивания не являются ошибкой формата.
- Нет требования к буквальному шаблону `speaker_N`: ТЗ требует строковый идентификатор.

Пустая расшифровка, пустые строки, нулевая длительность, дополнительные поля,
выход за длительность файла и нарушение порядка начала реплик выводятся как
предупреждения. ТЗ не устанавливает для них все правила; инструмент не
выдаёт свои рекомендации за официальные ограничения.

Коды завершения: `0` — проверка/расчёт выполнены; `2` — ошибка ввода или
невалидный экспорт. У `validate --fail-on-warnings` код `1` означает предупреждения.
`score` не устанавливает проходной WER: такую границу нужно выбрать отдельно.

JSON Schema в `schemas/nuclear_transcript.schema.json` описывает поля и типы
со слайда 15. Python дополнительно проверяет временную согласованность и
лексическую целочисленность: `1000.0` считается ошибкой экспорта, хотя некоторые
JSON Schema валидаторы принимают численно целый float.

## Как считается качество

`WER = (substitutions + deletions + insertions) / reference_words`.

Делитель — число слов эталона. WER может превышать 100% при множестве вставок.
При пустом эталоне WER выводится как `null`; ошибка не маскируется значением 0%.
Используется точное расстояние Левенштейна с линейной памятью и квадратичным
временем. Для многочасовых записей считайте отдельно по согласованным фрагментам
или используйте специализированный scorer. Разбиение меняет допустимые выравнивания;
числа разных схем разбиения нельзя автоматически считать эквивалентными.

При нескольких минимальных выравниваниях предпочтение: диагональ, удаление,
вставка. Отдельные S/D/I зависят от этого выбора, сумма ошибок и WER — нет.

Нормализация `ru-basic`:

1. Unicode NFC, casefold, `ё` → `е`.
2. Любая Unicode-пунктуация заменяется пробелами. В том числе «из-за» → «из за».
3. Разбиение по пробельным символам.
4. Цифры не превращаются в слова, числа и имена не исправляются.

`--normalization exact` выполняет только разбиение по пробелам, сохраняя
регистр и пунктуацию. Имя политики всегда записывается в отчёт.

**Официальная нормализация WER в презентации не задана.** Эти значения служат
для воспроизводимого сравнения своих версий при одинаковых данных и политике.
Объединение реплик идёт в порядке массива; идентификаторы спикеров при WER
игнорируются. Ошибки диаризации, перестановка speaker-ID и точность таймкодов
этой метрикой не оцениваются. DER здесь намеренно не реализован: нужны отдельный
эталон сегментов и согласованные правила overlap, collar и speaker mapping.

`RTF = elapsed_seconds / audio_seconds`. При RTF 0.5 обработка занимает
половину длительности записи. В отчёте явно указано `timing_source=caller_supplied`.

## Что измерять команде

1. Один и тот же аудиофайл, его длительность и эталон.
2. Телефон, RAM, Android, сборка приложения, версии и хеши весов.
3. Полное время основной цепочки: чтение/декодирование, диаризация, ASR,
   объединение и экспорт. Отдельно время загрузки моделей и LLM-сводки.
4. Холодный запуск и повторный запуск отдельно; одно и то же число потоков.
5. Пиковую память процесса, успешность завершения, результат проверки в авиарежиме.

Для прозрачности сохраняйте обе длительности: основная цепочка и полный
пользовательский сценарий с LLM. Официальную границу замера RTF нужно уточнить.
Сравнивать Mac с телефоном как один бенчмарк нельзя.

## Подключение к репозиторию

Файлы расположены в корне репозитория, запускать команды нужно оттуда.
Подключение не меняет Gradle, Android-пакеты или интерфейсы участников.
Скрипт пригоден и для текущей ASR-ветки, и для итогового приложения после экспорта.

Катя проверяет экспорт, Антон сравнивает варианты ASR, Артём использует
предупреждения о времени и проверяет диаризацию отдельно, Максим готовит
эталоны и фиксирует воспроизводимые замеры.
