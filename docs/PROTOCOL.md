# Формат результата и события обработки

Приложение обрабатывает локальный аудиофайл и экспортирует JSON. Сетевого или
акустического протокола передачи данных в этом проекте нет.

## JSON для сдачи

Экспорт формирует `ru.stenographer.core.TranscriptJson`:

```json
{
  "transcript": [
    {"speaker_id":"speaker_1","start_ms":1250,"end_ms":4380,"text":"Добрый день!"},
    {"speaker_id":"speaker_2","start_ms":4500,"end_ms":6200,"text":"Начнём обсуждение."}
  ]
}
```

| Поле | Тип | Значение |
|---|---|---|
| `transcript` | массив объектов | Реплики в порядке записи |
| `speaker_id` | строка | Постоянный ID голоса внутри одной записи |
| `start_ms` | целое число | Начало реплики от начала аудио, миллисекунды |
| `end_ms` | целое число | Конец реплики, миллисекунды; не раньше начала |
| `text` | строка | Распознанная речь |

В Kotlin время хранится как `Long`. Значения неотрицательные; секунды и дробные
миллисекунды в эти поля не записываются. Проект нумерует голоса `speaker_1`,
`speaker_2` и далее по первому появлению; это не идентификация личности.
ID из разных файлов не обозначают одного и того же человека. Пересечения
интервалов разрешены. Отсутствие речи может дать пустой массив.

Слова, огибающая, характеристики голоса и конспект не добавляются в JSON задания.
Конспект сохраняется отдельно и не переписывает исходную расшифровку.
Схема — [nuclear_transcript.schema.json](../schemas/nuclear_transcript.schema.json).
Проверка: `python tools/nuclear_quality.py validate exported.json`.

## Внутренний контракт Kotlin

`TranscriptionPipeline.process(fileId, uri)` возвращает холодный
`Flow<PipelineEvent>`: работа начинается при подписке. Все события содержат
`fileId`, чтобы интерфейс не смешивал разные записи.

| Событие | Полезная нагрузка и назначение |
|---|---|
| `StageProgress` | Этап `DECODE`, `DIARIZE`, `RECOGNIZE`, `MERGE`, `SUMMARY`; прогресс 0…1 внутри этапа |
| `Decoded` | Длительность в мс и RMS-огибающая: одно значение 0…1 на 50 мс |
| `SpeakerFound` | Найденный голос и момент первого появления |
| `Segments` | Порция интервалов голосов; `final=true` обозначает последнюю порцию |
| `SpeakerFeatures` | Медианная высота, её разброс и средняя громкость для визуализации голоса |
| `Words` | Очередная порция распознанных слов и `processedUntilMs` |
| `Done` | Готовые реплики `List<Utterance>`, доступные для экспорта |
| `Summary` | Название, текст конспекта и пункты со ссылками на исходные реплики |
| `Failed` | Ошибка основной обработки, её текст можно показать пользователю |

Последовательность: декодирование → голоса/сегменты → слова → `Done` →
`Summary`, если локальная LLM включена и отработала успешно. Прогресс приходит
между событиями. Характеристики голосов предусмотрены контрактом; их отправка
реализована в обновлении pipeline, поэтому потребитель допускает их отсутствие.

**`Done` означает готовность расшифровки, а не окончание Flow.** Очередь должна
дождаться завершения Flow, прежде чем начинать следующий файл: после `Done`
модель ещё может строить конспект. Отмена подписки отменяет обработку;
`CancellationException` не превращается в `Failed`.

Ошибка LLM не отменяет уже полученный `Done`: готовый текст остаётся доступен,
событие `Summary` не приходит, причина записывается в журнал. Отдельного события
ошибки конспекта пока нет. Потребитель завершает ожидание конспекта при завершении
Flow, а не ждёт `Summary` бесконечно. После `Failed` обработка файла прекращается.

## Пункты конспекта

`SummaryPoint(text, sourceStartMs, kind, speakerId)` содержит дословный фрагмент,
начало его исходной реплики, раздел `topic` / `decision` / `task` и ID говорящего.
Время и голос подставляет код из исходных данных, LLM их не генерирует.
Для совместимости двухаргументные вызовы разрешены: `kind="topic"`, `speakerId=null`.
Название приводится к 3–6 словам; ошибка его длины не удаляет корректные пункты.

Сырой ответ LLM содержит только `title`, `topic`, `decisions`, `tasks`, а пункты —
только разрешённые `source_id`. Это внутренний формат отбора, он не экспортируется
вместо транскрипции. Текст фрагментов и исходные ID говорящих не выполняются как код.

## Отчёт диагностического бенча

`bench_*.json` не равен JSON задания: он хранит слова, события и замеры.
`transcription_ms` — время до `Done`; `rtf = transcription_ms / 1000 / audio_seconds`.
`processing_ms` — время до завершения Flow, включая попытку построения конспекта.
Новый бенч фиксирует `processing_scope=until_flow_completion_before_export`:
запись экспортных файлов выполняется после этих замеров. В старых отчётах без
этой метки `processing_ms` мог включать экспорт; инструмент сохраняет это различие.
`summary_status`
показывает, был ли конспект успешно получен. `peak_rss_mb` — накопительный максимум
памяти процесса, а не собственная память отдельного этапа.

`score-bench` различает этот формат и старый ASR-бенч без `transcription_ms`.
Он выводит `rtf` до расшифровки и отдельно `full_rtf` до завершения pipeline.
Бенч с ошибкой основной обработки не получает оценку успешного прогона.
